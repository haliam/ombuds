# ADR-0010: pgvector inside Postgres, accessed via psycopg3 + plain SQL

**Status:** accepted
**Date:** 2026-10-06

## Context
The data-layer stage needs durable state (approval requests, claims, long-term memory) and a vector store for the RAG knowledge base. ADR-0009 requires the approval store to be shared across processes (the MCP subprocess and the API) and the `APPROVED → EXECUTED` transition to share a transaction with the executor's write. The options were a separate vector DB (Chroma) next to Postgres, or the pgvector extension inside the same Postgres; and for access, an ORM (SQLAlchemy + Alembic) or a plain driver (psycopg3) with SQL migrations.

## Decision
Store embeddings in a `kb_chunks` table using pgvector in the same Postgres as the relational data, and access it through psycopg3 with hand-written SQL and numbered `.sql` migrations.

## Consequences
- One database container and one transaction boundary: a claim, its approval and its retrieved chunks can be joined and committed together, and integration tests need a single Docker service.
- Atomic compare-and-set transitions (`UPDATE ... WHERE status = ...`) and `INSERT ... ON CONFLICT` dedup are written directly, which is what ADR-0009's single-execution guarantee depends on.
- Vector search runs on Postgres' planner and an HNSW index; fine at KB scale (hundreds to thousands of chunks), not tuned for tens of millions of vectors.
- No ORM means row-to-model mapping is written by hand in the repositories, and migrations are not autogenerated.
- Revisit if the KB grows past roughly a million chunks or vector search latency starts competing with transactional load; at that point a dedicated vector store behind the `VectorStore` Protocol is a drop-in change.

## Alternatives considered
- **Chroma as a separate service** — simple API, but a second container, no transactional link to claim data, and a second persistence story to test and back up.
- **SQLAlchemy 2 + Alembic** — conventional and autogenerates migrations, but adds an abstraction layer over the few explicit statements this schema needs.
