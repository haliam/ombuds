## Version 1: steps and decisions

**Source** `docs/progress/tasks.md`, `docs/decisions/`; generated by [`development_board_gen.py`](../development_board_gen.py)

![development-overview](development-overview.png)

Source: [`development-overview.json`](development-overview.json)

### What it shows

The four-week build as a board: each step (done or pending), the ADR decisions with their dates, a marker for where the project is now, flagged gaps and a glossary of key terms. Version 1 includes the key decisions.

### Like I'm 5

This board is the project's to-do list drawn as a map. Week 1 is the basics (rules, calling the AI, tools). Week 2 is the agent loop and the tool server. Week 3 is the rule book search, the database, Docker and the safety checks. Week 4 is watching, policy and polish. The board marks what is done, what is still to do, and where we are now.

### For an interviewer

The build ran in four weekly slices: API fundamentals, the agent loop and MCP, RAG with the data layer, Docker and guardrails, then observability and governance, with a refactor between weeks 3 and 4 after review. Every real alternative is recorded as an ADR and dated on the board. The board lists the gaps on purpose: tracing, the Rego payout policy and the audit trail are still stubs, and the end-to-end eval dataset is empty.

### Likely follow-up

Which decision would you revisit first? ADR-0008 (in-memory, poll-based approval) was superseded by ADR-0009 (the approval request is the pending action, stored in Postgres).

## Version 2: steps with code links

**Source** `docs/progress/tasks.md`; generated from `development-overview-v2.json`

![development-overview-v2](development-overview-v2.png)

Source: [`development-overview-v2.json`](development-overview-v2.json)

### What it shows

The same build history as version 1, reduced to steps only, with each step linked to its code at a fixed commit.

### Like I'm 5

It is the same map as the first board, but every step has a link, so you can click from a step such as 'Human approval' straight to the code that does it.

### For an interviewer

Where v1 explains the decisions, v2 is the evidence: each step points at the code at a pinned commit, so a claim like 'approvals are exactly-once' can be checked in the source rather than taken on trust.

### Likely follow-up

Why two boards? One is for narrating decisions, the other for proving the steps exist in code.

## Regenerate

Edit the board's JSON (bump the version and date in `meta.title`), then from the repo root:

```bash
python docs/diagrams/render_archify.py development-overview      # v1
python docs/diagrams/render_archify.py development-overview-v2   # v2
```

This runs `archify finalize architecture` and rewrites the `.png` next to the JSON. `render_archify.py` maps `development-overview-v2` to this folder.

Board v1 is generated: edit [`development_board_gen.py`](../development_board_gen.py), run it to rewrite the JSON, then the command above. Board v2's JSON is edited by hand.
