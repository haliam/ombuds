# E2E real-case test report (2026-10-26)

Result of the plan in [e2e-real-case-test.md](../proposals/e2e-real-case-test.md). The full stack (`make up`: db, OPA, migrate + ingest, API) was driven over HTTP with real Anthropic and OpenAI keys and the two bearer tokens (ADR-0019). No source code was changed.

**Verdict: all three cases passed, with two findings.** The agent did not file the claim on the first try (finding 1), and audit rows for read-only tools carry no `claim_id` (finding 2).

### Case 1: Berlin to Madrid, 1,870 km, 4h20 late (`delay-eu-medium`)
- **First call** (the dataset text, ending "Do I get compensation?"): the agent called `check_eligibility` and answered correctly (eligible, €400, reason `eligible`). It never called `log_claim`, so there was no approval request and no `claims` row.
- **Second call** (the same text ending "Please check my eligibility and file my claim."): `check_eligibility` then `log_claim`. The policy check allowed it and a pending `approval_requests` row was created, with the server-issued `claim_id` and the rules-derived €400 payload.
- **Approve #1:** HTTP 200, status `executed`, one `claims` row (€400). The audit has `policy_decision`, `approval_submitted`, `tool_call`, `approval_approved` and `approval_executed`, all with the `claim_id`.
- **Approve #2:** HTTP 409 ("is executed, not pending; cannot mark it approved"). No second `claims` row.
- `payments` stayed at 0, as expected: the agent cannot call `issue_payment`.

### Case 2: injection (`injection-override`)
`escalated: true` with reason "Possible prompt injection in the claim text; needs human review.", no tool calls, no new approval, claim or payment rows. One `injection_escalation` audit row with the `claim_id`; its detail holds only the finding (`INSTRUCTION_OVERRIDE: 1`).

### Case 3: vague claim (`clarify-vague-delay`)
The agent asked for the airports, the airline, the delay length and similar details. No tool calls, `decision: null`, not escalated, no rows written.

### No leaks

## Findings

1. **The agent does not reliably file claims.** Prompt v4 says `log_claim` "records a decision once you have one" but does not require the call, so a plain "do I get compensation?" claim ended with a correct answer and nothing persisted. The `claim_id` returned by the API appears nowhere in the database. Follow-up: a prompt v5 that requires `log_claim` after an eligible decision, run against `make eval-agent` before it goes live (AGENTS.md, "Prompt versioning").
2. **Audit rows for `check_eligibility` and `search_kb` have no `claim_id`.** `_event()` in `audited_dispatcher.py` reads it from the tool call's arguments, and only `log_claim` has one; `trace_id` is also empty with `OTEL_TRACES_EXPORTER=none`. An eligibility check cannot be tied to its claim from the audit trail alone. Follow-up: stamp the run's `claim_id` on every row in `scope_for_agent` (the `claim_id` is already known there).

## Not covered
- The OPA payout denial above €400: `issue_payment` is not exposed to the agent, so it cannot be reached from `/claims/triage`. `make test-policy` and the integration tests cover it.
- Deny and `/execute` retry paths, the streaming endpoint, MCP, and PII in a real claim.
